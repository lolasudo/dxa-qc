# DXA QC - backend

Ядро сервиса: чтение DICOM, модели оценки качества, REST API, пакетная обработка и обучение.
Запуск и эксплуатация описаны в [корневом README](../README.md).

## Функциональность

Для каждого DICOM-снимка сервис возвращает:

| Результат | Описание |
|---|---|
| Анатомическая область и проекция | поясничный отдел позвоночника или проксимальный отдел бедра, прямая проекция (AP), для бедра - сторона. Определяется только по пикселям, имена файлов и теги не используются |
| `quality_class`, `quality_prob` | 0 - исследование качественное, 1 - есть нарушение; калиброванная вероятность нарушения |
| `violation_type` | одно или несколько нарушений: некорректная укладка, не выровнена ось позвоночника, посторонние предметы, некорректная область интереса |
| Заключение | текст на русском с измерениями: наклон оси, размер поля, подозрение на эндопротез |
| Коррекция | что изменить в укладке или поле сканирования; применяется после решения специалиста |
| Визуализация | PNG-превью в физических пропорциях и прозрачный слой разметки |
| DICOM-серии | Enhanced SR с заключением и Secondary Capture с разметкой, в исследование исходного снимка |

Режимы: REST API (используется веб-интерфейсом) и CLI для файла, папки или ZIP. Сетевых обращений
при работе нет.

Результат носит вспомогательный характер. Модели обучены примерно на 100 исследованиях с
экспертной разметкой; ограничения по качеству описаны в разделе [Качество](#качество).

## Архитектура

```
файл / папка / ZIP
  -> ingest       безопасная распаковка, отбор DICOM
  -> dicom_io     чтение и валидация, нормализация, изотропная сетка 1 мм
  -> models       область и сторона -> геометрия + эмбеддинги -> решения по критериям
  -> report       строка отчёта (xlsx/csv), журнал ошибок
  -> outputs      заключение, коррекции, PNG, DICOM SR и Secondary Capture
```

| Пакет `dxa_qc` | Ответственность |
|---|---|
| `config` | загрузка `configs/*.yaml` со строгой валидацией |
| `domain` | справочники областей и нарушений, сборка `violation_type` |
| `ingest` | обход папок и ZIP; защита от zip-slip, zip-bomb, symlink, переполнения диска |
| `dicom_io` | чтение DICOM с лимитами, `PixelSpacing` из тега или из конфигурации |
| `models.region` | классификатор «позвоночник / правое бедро / левое бедро» |
| `models.quality` | геометрия в мм, замороженные бэкбоны, линейные головы, калибровка |
| `pipeline` | обработка пакета, изоляция ошибок по файлам, общие выходы API и CLI |
| `explain` | заключение, проекция, предложения по коррекции |
| `visualization` | превью и слой разметки |
| `report` | схема отчёта, xlsx/csv, DICOM SR и Secondary Capture |
| `api` | FastAPI, очередь задач, лимиты, решение специалиста |
| `cli` | `python -m dxa_qc.cli.batch_process` |
| `training` | манифест, обучение, метрики с bootstrap-ДИ, анализ ошибок |
| `data` | разметка организатора, аннотации областей, манифест обучения |

Конфигурация: `configs/thresholds.yaml` (клинические пороги, лимиты чтения), `configs/service.yaml`
(лимиты API), `configs/training.yaml` (обучение).

## Зависимости

- Python 3.11; версии всех пакетов зафиксированы в `requirements-dev.lock`.
- Базовый образ `python:3.11-slim-bookworm` (по дайджесту), torch 2.11.0 (CPU или CUDA 12.8), timm,
  safetensors, scikit-learn, FastAPI, uvicorn, pydicom, numpy, scipy, openpyxl.
- Веса `weights/`: `region_classifier.npz`, `quality_spine.npz`, `quality_hip.npz`,
  `backbones/*.safetensors` (EfficientNet-B3, ConvNeXt-S, DINOv2 ViT-S/14). Используются только
  форматы `.npz` с JSON и safetensors, без pickle. При загрузке бэкбоны сверяются по sha256 с теми,
  на которых обучены головы: подменённый файл приводит к ошибке, а не к неверным прогнозам.

Локальная установка:

```bash
py -3.11 -m venv .venv                                  # Linux/macOS: python3.11 -m venv .venv
.venv/Scripts/python -m pip install --extra-index-url https://download.pytorch.org/whl/cu128 \
    -r requirements-dev.lock -e ".[ml,api,train,dev]"
python -m dxa_qc.api --port 8000 --reload
python -m dxa_qc.cli.batch_process --input "../Датасет/Для теста.zip" --output out --series
pytest && ruff check src tests
```

## REST API

Префикс `/api/v1`. OpenAPI доступен на `/api/v1/docs` в режиме разработки; в Docker он скрыт
(`DXA_QC_API_DOCS=1` включает).

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | состояние сервиса и готовность моделей |
| POST | `/batch` | ZIP или DICOM (`multipart/form-data`, поле `file`), ответ `202 {job_id}` |
| GET | `/batch/{job_id}/status` | `queued`, `running`, `done`, `failed`; прогресс |
| GET | `/batch/{job_id}/results` | строки отчёта с проекцией, заключением, критериями, измерениями, коррекциями, решением специалиста и ссылками на файлы |
| GET | `/batch/{job_id}/result` | ZIP-архив с отчётами, визуализациями и DICOM-сериями |
| GET | `/batch/{job_id}/images/{n}/preview.png`, `overlay.png` | снимок и слой разметки |
| GET | `/batch/{job_id}/dicom/{n}/sr.dcm`, `sc.dcm` | DICOM SR и Secondary Capture |
| POST | `/batch/{job_id}/rows/{n}/review` | решение специалиста, только `application/json` |
| POST | `/study` | один DICOM, синхронно, таймаут 180 с |

Тело решения специалиста:

```json
{"decision": "confirmed"}
{"decision": "corrected", "quality_class": 1, "violations": ["Некорректная укладка"], "comment": "..."}
```

Коды ошибок:

| Код | Причина |
|---|---|
| 400 | пустой файл |
| 404 | задача, строка или файл не найдены (в том числе удалены по сроку хранения) |
| 409 | задача ещё выполняется или завершилась ошибкой |
| 413 | превышен размер загрузки |
| 415 | файл не ZIP и не DICOM |
| 422 | `/study` не смог обработать файл; решение специалиста противоречит строке |
| 429 | очередь заполнена, есть заголовок `Retry-After` |
| 503 | превышен лимит соединений |
| 504 | `/study` дольше 180 с |
| 507 | нет места в хранилище задач |

Лимиты настраиваются в `configs/service.yaml`, см. [DEPLOYMENT_GUIDE](../docs/DEPLOYMENT_GUIDE.md#лимиты).
Обращения к данным пациентов (загрузка, просмотр, скачивание, решение специалиста) пишутся в
журнал `dxa_qc.audit` с ID задачи и адресом клиента.

## Форматы данных

### Вход

DICOM-файл, папка любой вложенности или ZIP. Обрабатываются файлы с расширением `.dcm` или с
сигнатурой `DICM`; остальные пропускаются. Поддерживаются одноканальные однокадровые снимки
MONOCHROME1/2, 8 и 16 бит. При отсутствии `PixelSpacing` размер пикселя берётся из
`configs/pixel_spacing.yaml`.

### Отчёт

`results.xlsx` или `results.csv`, одна строка на снимок:

| Колонка | Значение |
|---|---|
| `path_to_study` | путь файла внутри входа |
| `study_uid`, `image_uid` | `StudyInstanceUID`, `SOPInstanceUID` |
| `anatomical_region` | `Поясничный отдел позвоночника` или `Проксимальный отдел бедра` |
| `quality_class` | 0 или 1 |
| `quality_prob` | вероятность нарушения, 0-1 |
| `violation_type` | нарушения через `;` в фиксированном порядке, пустая строка - нарушений нет |
| `processing_status` | `Success` или `Failure` |
| `time_of_processing` | время обработки снимка, с |

Значения `violation_type`: `Некорректная укладка`, `Не выравнена ось позвоночника`,
`Присутствуют посторонние предметы`, `Некорректная область интереса`. Для строк `Failure`
причина записывается в `results_errors.csv`.

### Дополнительные выходы

Формируются в API всегда, в CLI - с флагом `--series`.

| Файл | Содержимое |
|---|---|
| `results_details.csv` | проекция, заключение, вероятности по критериям, измерения, коррекции |
| `visualization/NNNNN_preview.png`, `NNNNN_overlay.png` | снимок и слой разметки |
| `dicom/NNNNN_sr.dcm` | Enhanced SR, серия 9901: область, проекция, вердикт, вероятность, нарушения, заключение, измерения (NUM, UCUM), рекомендации, ссылка на исходный снимок |
| `dicom/NNNNN_sc.dcm` | Secondary Capture, серия 9902: RGB-снимок с разметкой, 0,5 мм на пиксель |
| `results_reviewed.csv` | только API: решение специалиста рядом с решением модели |

Атрибуты пациента и исследования копируются из исходного снимка; значения, не соответствующие
формату DICOM (например, `Anonymized` в поле даты), пропускаются. После решения специалиста SR
перевыпускается с новым SOPInstanceUID и `VerificationFlag = VERIFIED`. Для строк `Failure`
визуализация и DICOM не создаются.

## Модель

### Предобработка

1. Проверка размера файла, изображения и физического размера поля до декодирования пикселей.
2. Нормализация интенсивности и пересчёт на изотропную сетку 1 мм. Пиксель сканера 1,05 x 0,6 мм,
   и без пересчёта наклон 5° выглядел бы как 8,7°.
3. Определение области и стороны: HOG 64x64 и логистическая регрессия.
4. Приведение бедра к одной ориентации, чтобы обе стороны обрабатывала одна модель.

### Определение области

Эталон - ручная проверка всех 252 уникальных снимков (`data/region_annotations.csv`).

| Подход | Точность, 5-fold по исследованиям |
|---|---|
| Эвристика: симметрия и смещение центроида | 98,8% |
| HOG 64x64, логистическая регрессия, зеркальная аугментация | 100% |

Инференс занимает около 1 мс на CPU. При уверенности ниже 0,6 (`region.min_confidence`) снимок
получает `Failure`, а не предположительную область.

### Оценка качества

По каждому критерию - ансамбль трёх логистических голов с равными весами (среднее логитов):

| Область | Геометрические признаки | Бэкбоны (заморожены) |
|---|---|---|
| Позвоночник | наклон центральной линии (робастная регрессия), наличие гребней подвздошных костей и рёбер в поле, яркие включения в мягких тканях | EfficientNet-B3, DINOv2 ViT-S/14 |
| Бедро | размеры поля, отступы кости от краёв, ось диафиза, профиль медиального контура | ConvNeXt-S, DINOv2 ViT-S/14 на зоне малого вертела |

### Постобработка

- Решения принимаются по порогам на исходных скорах; пороги оптимизируют F1 на out-of-fold
  предсказаниях. Калибровка Platt используется только для вероятностей.
- `quality_prob` строится по отдельной голове на итоговую оценку эксперта в сочетании с
  максимумом по критериям. Итоговая оценка эксперта не всегда равна «ИЛИ» по критериям:
  например, сколиоз даёт нарушение без отдельного флага.
- Любое нарушение означает `quality_class = 1`.
- Заключение, коррекции и визуализация строятся по тем же измерениям, что и решение модели.
  Количественная коррекция предлагается только для оси позвоночника: для бедра измеренные отступы
  и наклон диафиза не разделяют нормальные и нарушенные снимки (AUC 0,52-0,59), поэтому
  рекомендация даётся в виде правила без чисел.

## Качество

### Данные

- 100 исследований, 499 файлов, 252 уникальных снимка; остальное - побайтовые дубли внутри
  исследования. Пересечений между исследованиями нет.
- В разметке 1 означает нарушение. Разметка дана по исследованию и области без привязки к файлу,
  поэтому сторона бедра определяется по изображению.
- Теги `PixelSpacing`, `BodyPartExamined`, `Laterality` отсутствуют; все снимки 8-bit MONOCHROME2
  около 300x300.
- Нарушения: позвоночник 32 из 99 (посторонние предметы 17, ось 10, укладка 6), бедро 41 из 150
  (укладка 36, область интереса 7).

### Методика

20 повторов StratifiedGroupKFold(5) с группировкой по исследованию. Пороги и калибровка для
каждого фолда подбираются только на остальных фолдах. 95% доверительные интервалы - bootstrap по
исследованиям, 1000 ресэмплов. Полный отчёт - `weights/quality_metrics.json`.

### Результаты

| Область / цель | Нарушений | ROC-AUC | PR-AUC | F1 | Чувств. | Специф. |
|---|---|---|---|---|---|---|
| Позвоночник, `quality_class` | 32 / 99 | 0,86 [0,77-0,94] | 0,75 [0,61-0,91] | 0,71 [0,59-0,79] | 0,80 | 0,78 |
| - укладка | 6 | 0,83 [0,47-1,00] | 0,72 | 0,65 | 0,53 | 0,99 |
| - ось | 10 | 0,83 [0,71-0,93] | 0,42 | 0,40 | 0,54 | 0,87 |
| - посторонние предметы | 17 | 0,88 [0,76-0,98] | 0,69 | 0,71 | 0,76 | 0,92 |
| Бедро, `quality_class` | 41 / 150 | 0,73 [0,61-0,83] | 0,63 [0,47-0,78] | 0,53 [0,39-0,65] | 0,55 | 0,80 |
| - укладка | 36 | 0,71 [0,57-0,83] | 0,51 | 0,49 | 0,52 | 0,81 |
| - область интереса | 7 | 0,79 [0,47-0,97] | 0,57 | 0,55 | 0,56 | 0,96 |
| Обе области, `quality_prob` | 73 / 249 | 0,78 [0,71-0,84] | 0,66 [0,55-0,78] | 0,61 [0,54-0,68] | 0,66 | 0,79 |
| Определение области и стороны | 252 | точность 100% | | | | |

Macro-F1 по типам нарушений: позвоночник 0,59, бедро 0,52, все четыре типа 0,54. Brier score
`quality_prob`: 0,139 против 0,219 у прогноза по доле нарушений (позвоночник), 0,163 против 0,199
(бедро). Опорная модель `--assessor prior_baseline` даёт ROC-AUC 0,5. Все файлы обучающего набора
обрабатываются успешно.

### Анализ ошибок

| Пометка эксперта | Позвоночник: снимков (нарушений) | Чувств. / специф. | Бедро: снимков (нарушений) | Чувств. / специф. |
|---|---|---|---|---|
| сколиоз | 14 (3) | 0,70 / 0,71 | 16 (0) | - / 0,85 |
| без пометок | 81 (27) | 0,79 / 0,79 | 129 (39) | 0,53 / 0,78 |

На сколиозе растёт число ложных срабатываний по позвоночнику: кривизна позвоночника похожа на
невыровненную ось. По другим пометкам (эндопротез, перелом, переходный позвонок) данных слишком
мало для выводов. В `quality_metrics.json` также есть список снимков, на которых модель ошибается
в большинстве повторов (22 снимка позвоночника, 35 бедра), - это материал для разбора с экспертом.

### Рассмотренные альтернативы

| Вариант | Результат |
|---|---|
| одна модель на всех геометрических признаках | переобучение (ось 0,56 против 0,84 у одного угла) |
| дообучение ResNet18 / ConvNeXt-T | укладка бедра 0,61-0,65 против 0,69-0,71 у замороженных признаков |
| ResNet50, DINOv2-B | хуже выбранных бэкбонов на большинстве критериев |
| обучаемые веса ансамбля (стекинг) | хуже равных весов на 0,02-0,08 AUC |
| решения по калиброванным вероятностям | при 4-5 положительных примерах калибровка вырождается, минус 0,01-0,07 AUC |
| детектор малого вертела по контуру | ненадёжен из-за наложения седалищной кости, оставлен слабым признаком |
| агрегация укладки по паре бёдер | +0,015 AUC, в пределах разброса между повторами |

### Ограничивающие факторы

- Мало примеров редких нарушений: 6 для укладки позвоночника и 7 для области интереса бедра,
  отсюда доверительные интервалы шириной около 0,5.
- Шум разметки: встречаются снимки с явными посторонними предметами и меткой 0; метки укладки
  для пары бёдер одного исследования совпадают в 61 из 72 случаев.
- Эксперты отмечали нарушение оси при наклоне 2-5°, то есть в пределах формальной нормы. Модель
  обучена на фактических решениях экспертов, а измеренный угол приводится в заключении.

Дальнейший рост качества зависит от данных: разметки ориентиров (малый вертел, Th12) и повторной
разметки вторым экспертом.

## Обработка ошибок

Ошибка в отдельном файле не прерывает пакет: файл получает статус `Failure`, причина пишется в
`results_errors.csv`. Пути сервера и тексты внутренних исключений в отчёт не попадают, они
пишутся только в журнал сервиса.

| Ситуация | Поведение |
|---|---|
| файл не DICOM, повреждён, нет или не декодируются пиксели | `Failure` с причиной |
| цветной, многокадровый, неподдерживаемый PhotometricInterpretation | `Failure` с причиной |
| слишком большой файл или неправдоподобный физический размер | `Failure` до декодирования пикселей |
| область не распознана уверенно | `Failure` |
| небезопасный архив или нет места на диске | вход отклоняется целиком: CLI - код 2, API - задача `failed` |
| нет весов или не совпадает sha256 бэкбона | CLI - код 2, API - `models_ready: false` |
| не удалось построить PNG или DICOM | строка отчёта сохраняется, ошибка пишется в журнал |
| перегрузка API | 413, 429, 503, 507 |

Коды выхода CLI: 0 - отчёт записан (отдельные файлы могут иметь `Failure`), 2 - вход, конфигурация
или веса непригодны.

## Воспроизводимость

Повторный запуск на тех же данных даёт тот же отчёт; это проверяется тестами. Порядок обхода
файлов фиксирован, модели детерминированы, UID DICOM-объектов выводятся из входных данных. На GPU
отключены TF32 и недетерминированные алгоритмы cuDNN: расхождение эмбеддингов с CPU, на котором
подобраны пороги, снижается с 2e-3 до 2e-6, а повторные запуски на GPU совпадают бит в бит.

## Ограничения

- Поддерживается только прямая проекция (AP) - других в обучающих данных нет.
- Для снимка с неуверенно распознанной областью возвращается `Failure`; разделитель в
  `violation_type` - `;` без пробела (настраивается в `configs/thresholds.yaml`). Оба решения
  требуют подтверждения организатором.
- Эндопротез, металл которого сканер маскирует как тёмную область, не распознаётся (1 случай в
  датасете).
- Первый снимок после старта обрабатывается 2-3 с из-за загрузки бэкбонов, последующие - 0,1-0,5 с.
- Состояние задач хранится в памяти процесса: после перезапуска backend задачи и решения
  специалистов недоступны через API (выгруженные архивы сохраняют их).

## Развитие

1. Разметка ориентиров (малый вертел, Th12) и повторная разметка вторым экспертом.
2. Дообучение на решениях специалистов из `results_reviewed.csv`, см.
   [TRAINING_GUIDE](../docs/TRAINING_GUIDE.md).
3. Отдельная обработка сколиоза для снижения ложных срабатываний по оси.
4. Хранение задач и решений в базе данных для длительной эксплуатации.
