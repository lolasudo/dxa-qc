# Безопасность

Сервис обрабатывает медицинские изображения в закрытом контуре. Меры ниже закрывают четыре риска:
утечку данных пациентов, несанкционированный доступ, отказ в обслуживании и выполнение чужого кода
через входные файлы, веса или цепочку поставок.

## Данные

- Работа полностью локальная: на инференсе нет сетевых обращений, backend физически не имеет
  выхода в интернет (внутренняя сеть Docker). `scripts/check_offline.sh` проверяет API и пакетную
  обработку в контейнере с `--network none`.
- Интерфейс не загружает внешние шрифты, CDN и аналитику (шрифт Golos встроен в сборку); CSP это
  запрещает.
- Загрузки, отчёты и превью удаляются через `job_ttl_hours` (24 ч). Ответы с данными пациентов не
  кэшируются. `/health` не раскрывает пути на сервере.

## Доступ и журнал

- Вход по паролю (HTTP Basic в nginx) включается `scripts/set_password.sh <логин>`; пароль хранится
  только в виде хеша (`apr1`), минимум 10 символов. Проверка готовности (`/healthz`,
  `/api/v1/health`) доступна без пароля.
- Без TLS пароль и данные передаются открыто: в сети используйте HTTPS-прокси
  ([DEPLOYMENT_GUIDE](DEPLOYMENT_GUIDE.md#пароль-и-https)).
- Журнал аудита - строки логгера `dxa_qc.audit` в `docker compose logs backend`:
  `upload job=<id> kind=batch client=<ip>`, `view-results ...`, `download-archive ...`,
  `download-dicom job=<id> index=<n> kind=sr|sc ...`, `review job=<id> index=<n> decision=... ...`.

## Решение специалиста и DICOM-выходы (2026-09-26)

- `POST /batch/{id}/rows/{n}/review` принимает только `application/json`: запрос с `text/plain` или
  формы отклоняется (422, закреплено тестом). Поэтому чужой сайт не может отправить решение от
  имени вошедшего пользователя без CORS-preflight, а CORS по умолчанию выключен (защита от CSRF
  при входе по паролю, который браузер подставляет сам).
- Тело проверяется строго: неизвестные поля запрещены, комментарий до 1000 символов, не более 10
  нарушений, и только из списка критериев этой области. Текст комментария в `results_reviewed.csv`
  защищён от formula injection.
- DICOM SR и Secondary Capture отдаются с `Cache-Control: no-store`, пишутся в каталог задачи и
  удаляются вместе с ней по TTL. Новых персональных данных в них нет: атрибуты пациента копируются
  из исходного снимка, как их прислал пользователь.
- Повторная проверка: bandit - 0, ruff - 0, shellcheck - 0; 352 теста backend и 28 тестов frontend
  проходят.

## Входные файлы

- **Архивы:** защита от zip-slip, symlink, zip-bomb (лимит коэффициента сжатия, числа файлов и
  распакованного объёма) и от распаковки, после которой на диске останется меньше
  `ingest.min_free_disk_bytes`.
- **DICOM:** лимиты размера файла и изображения; физический размер поля проверяется **до**
  декодирования пикселей, изотропная пересборка ограничена 4096 px. Файл, созданный, чтобы
  исчерпать память, получает `Failure` и не валит процесс.
- **Отчёты:** значения, начинающиеся с `= + - @`, табуляции или CR, экранируются (formula injection
  в XLSX/CSV).

## Отказ в обслуживании

- nginx ограничивает частоту запросов (API - 20 r/s, загрузка - 10 r/min на IP) и число соединений
  на IP, задаёт таймауты против slowloris и лимит тела 2 ГБ.
- Backend (`api/limits.py`) считает фактически полученные байты, в том числе при chunked-передаче,
  и обрывает чтение при превышении лимита. Очередь задач, синхронные запросы, хранилище и
  свободное место ограничены (коды 429/507 с `Retry-After`), uvicorn ограничивает число соединений
  (503).
- Контейнеры ограничены по памяти, CPU и числу процессов.

## Контейнеры

- Процессы работают не от root (uid 10001 и 101), корневая ФС только для чтения, запись - только в
  tmpfs (`noexec,nosuid,nodev`) и том задач; `cap_drop: ALL`, `no-new-privileges`, файлов с
  setuid/setgid нет.
- Backend не публикуется наружу и не имеет выхода в интернет; доступ к нему - только через nginx.
- В runtime-образе backend нет pip, setuptools, ensurepip и исходников.
- Веса монтируются только для чтения. Форматы - `.npz` + JSON (`allow_pickle=False`) и safetensors,
  pickle не используется. При загрузке sha256 каждого бэкбона сверяется с записанным в модели.

## Цепочка поставок

Проверки в CI (`.github/workflows/ci.yml`) на каждый push:

| Проверка | Инструмент |
|---|---|
| Статический анализ Python | ruff, bandit |
| SAST: Python, OWASP Top 10, React/TS, Dockerfile, nginx, GitHub Actions, секреты | Semgrep |
| Уязвимые зависимости Python / npm | pip-audit, npm audit |
| Уязвимости в собранных образах (HIGH/CRITICAL с исправлением - сборка падает) | trivy |
| Ошибки конфигурации Dockerfile / compose | trivy config |
| Секреты во всей истории git | gitleaks |
| Скрипты | shellcheck |
| Перечень компонентов (SBOM, CycloneDX) | syft, артефакт сборки |

Сканеры запускаются из официальных образов с закреплёнными версиями; официальные actions
закреплены по SHA. Базовые образы закреплены по дайджесту, зависимости - lock-файлами.
Dependabot еженедельно предлагает обновления, но не раньше чем через 7 дней после выхода версии.

## Соответствие HIPAA Security Rule (технические меры, §164.312)

| Требование | Как выполнено |
|---|---|
| (a) контроль доступа | вход по паролю (опционально), случайные ID задач, автоматическое удаление через 24 ч |
| (b) контроль аудита | журнал `dxa_qc.audit` |
| (c) целостность | sha256 бэкбонов, неизменяемые образы, read-only ФС |
| (d) аутентификация | HTTP Basic через nginx; для нескольких пользователей и SSO - внешний прокси |
| (e) защита при передаче | локальная обработка; для сети - HTTPS-прокси (TLS в сервис не встроен) |

Организационные меры (анализ рисков, BAA, обучение персонала) - ответственность оператора
сервиса.
